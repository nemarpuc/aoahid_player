# Code review, October 2026

A review of all three repositories (libaoahid 4.0.3, aoahid_adb_proxy 3.1.0,
aoahid_player 1.0.2): defects, edge cases, cross-repository mismatches, and
performance on the input path. Part 1 lists what was fixed and in which
release. Part 2 lists what was found and left open, with a proposed change.
How the repositories depend on each other is in [CROSS_REPO.md](CROSS_REPO.md).

Method: reading the code, the existing test suites, new tests for the fixes,
a ThreadSanitizer run of libaoahid, and the GUI driven through its control
API against libaoahid's fake USB backend. **Nothing here was verified on a
phone.** Severity is the effect on a user; effort is S (under an hour),
M (a day), L (more).

Source references are `repo/path#Lnnn`, valid at libaoahid v4.0.4,
aoahid_adb_proxy v3.1.2, and aoahid_player v1.1.0.

## Part 1: fixed

### P1. First input can be sent before Android has registered the HID device

- Where: `aoahid_player/src/session.cpp#L148`.
- Why: `aoahid_node_open` returns when the descriptor has been sent. Android
  creates the input device after that. A report sent in between is refused
  with a STALL, and `DeviceGroup::fail` then closes the phone ("refused a
  report and was dropped"). `aoa_touch` went from connect to the first row
  with nothing in between; libaoahid's `docs/API.md` asks for a gap of about
  100 ms.
- Change:

  ```cpp
  // before
      setup_ = setup;
      return true;
  // after
      setup_ = setup;
      Timing::sleep_ms(registration_settle_ms);   // 100
      return true;
  ```

- Effect: every front end is covered, since all of them connect through
  `Session`. Connecting takes 100 ms longer. Not covered by an automated test.

### P2. A stop that arrives as playback ends cancels the next playback

- Where: `aoahid_player/apps/aoahid_player_gui/engine.cpp#L409`,
  `aoahid_player/src/player.cpp#L84`.
- Why: Player controls are bits that the next `run()` consumes. `Engine::stop`
  posts one whenever a play command is running, but between the last `run()`
  returning and the command finishing (for a playlist, also between two
  steps) no `run()` is left to consume it. It stayed set, and the next
  playback stopped as soon as it started. A `/seek` in the same window moved
  the next playback instead.
- Change: `Engine::finish_run` drops pending controls under the mutex that
  `stop()` posts under, in the same critical section that lets the next play
  be queued.

  ```cpp
  // after, in Engine::finish_run()
      const std::lock_guard lock(mutex_);
      player_.discard_requests();
      running_play_ = false;
  ```

- Effect: none on a control posted before a playback starts; those still
  apply to it. `Player`'s header now states this. Checked by stopping and
  starting playback through the control API on the fake backend; the race
  itself has no automated test.

### P3. Live input can be slept through while a script waits

- Where: `aoahid_player/src/player.cpp#L368` and
  `hold_paused`.
- Why: the wake counter was read after the live pump ran. Input queued in
  between raised the counter before it was read, so the wait that followed
  saw nothing new and slept until the next script row, or indefinitely while
  paused.
- Change: read the counter first.

  ```cpp
  // before
      if (live_pump_) live_pump_();
      const uint32_t seen = wake_.epoch();
  // after
      const uint32_t seen = wake_.epoch();
      if (live_pump_) live_pump_();
  ```

### P4. A row with more contacts than declared drops the phone

- Where: `aoahid_player/src/device_group.cpp#L163`.
- Why: libaoahid returns `AOAHID_ERR_OVERFLOW` when a touch needs more slots
  than the Spec declares. `DeviceGroup::apply` treated only `AOAHID_ERR_PARAM`
  as a bad row; anything else closed the device. A recording from a
  ten-finger panel played with fewer contacts configured disconnected the
  phone.
- Change: `AOAHID_ERR_OVERFLOW` is handled like `AOAHID_ERR_PARAM`: the row is
  skipped with a warning and the device stays.

### P5. Recorder applies events of an untracked touch slot to another slot

- Where: `aoahid_player/src/getevent_parser.cpp#L237`.
- Why: an `ABS_MT_SLOT` of 16 or more left the previous slot selected, so the
  position and tracking-id lines that followed changed that slot.
- Change:

  ```cpp
  // before
      if (raw < max_slots)
          state.slot = raw;
  // after
      state.slot = raw < max_slots ? raw : max_slots;   // max_slots selects none
  ```

- Test: "GeteventParser drops events for a slot it does not track".

### P6. A recording that fails deletes an existing script of the same name

- Where: `aoahid_player/src/recorder.cpp#L127`.
- Why: `Recorder::run` truncated the target before adb had been started and
  removed it when adb could not start or nothing was captured.
  `aoa_record -o login` with no phone authorised deleted `csv/login.csv`.
- Change: rows are written to `<name>.part`. It replaces `<name>` only when
  the recording stops with at least one row; otherwise it is deleted and
  `<name>` is not touched.
- Effect: while recording, the file under its final name does not exist yet.
  A recording that is killed leaves a `.part` file with the rows written so
  far.
- Test: "A recording only replaces an existing script once it holds rows".

### P7. `aoa_touch` offset prompt accepts `nan` and `inf`

- Where: `aoahid_player/apps/aoa_touch/main.cpp#L266`.
- Why: `strtod` reads both, and the conversion to `int64_t` is then undefined.
- Change: the value must be finite and at most 1e9 ms in magnitude.

### G1. A mistyped boolean in the control API silently becomes the default

- Where: `aoahid_player/apps/aoahid_player_gui/control_api.cpp#L132`.
- Why: `POST /key?usage=a&down=flase` answered `ok` and pressed the key,
  because an unrecognised value took the default (`true`). The release never
  arrived.
- Change: a parameter that is absent still takes its default. One that is
  present and not `true`/`false`, `1`/`0`, `on`/`off`, or `yes`/`no` answers
  400. Twelve call sites.

### G2. `/seek` overflows for a very large `time_ms`

- Where: `aoahid_player/apps/aoahid_player_gui/control_api.cpp#L545`.
- Change: `time_ms` above `INT64_MAX / 1000000` answers 400.

### G3. Simultaneous `/play` requests queue several playbacks

- Where: `aoahid_player/apps/aoahid_player_gui/engine.cpp#L77`.
- Why: the phase was checked outside the lock that queues the command. Two
  HTTP threads could both pass and both queue; Stop removed only one.
- Change: the check and the queueing share one lock. `Engine::play` returns
  whether it queued, and `/play` answers 409 when it did not.

### G4. A second program can bind the control API's port and take requests

- Where: `aoahid_player/apps/aoahid_player_gui/control_api.cpp#L316`.
- Why: cpp-httplib sets `SO_REUSEPORT` on a listening socket by default. On
  Linux that lets another process, including a second copy of the GUI, bind
  the same address and port; the kernel then spreads connections across the
  listeners. The "already in use" message never appeared.
- Change: the server sets `SO_REUSEADDR` only (`SO_EXCLUSIVEADDRUSE` on
  Windows). Checked on Linux: a second bind with `SO_REUSEPORT` now fails
  with `EADDRINUSE`. The Windows branch was compiled in CI but not run.

### G5. `nan` in the settings file is accepted for a float

- Where: `aoahid_player/apps/aoahid_player_gui/settings.cpp#L78`.
- Change: `if (!(value >= minimum && value <= maximum)) return;`, which also
  rejects `nan`. The old form, `value < minimum || value > maximum`, is false
  for `nan`.

### G6. Settings file rewritten on every frame while the window moves

- Where: `aoahid_player/apps/aoahid_player_gui/app.cpp#L305`.
- Why: the window geometry is part of the settings and changes on every frame
  of a drag or resize, so the file was written at the frame rate on the UI
  thread, which also forwards live input.
- Change: nothing is saved on a frame whose geometry differs from the frame
  before. The first frame at rest saves.

### G7. Folded live mouse deltas can overflow `int32`

- Where: `aoahid_player/apps/aoahid_player_gui/engine.cpp#L20`.
- Change: moves and wheel steps folded in the inbox saturate.

### G8. Header status row overruns its right margin

- Where: `aoahid_player/apps/aoahid_player_gui/app_shell.cpp#L98`,
  `aoahid_player/apps/aoahid_player_gui/widgets.cpp#L748`.
- Why: the row is right-aligned from a computed width, and the computation
  counted one gap per divider where two are drawn. The row ended 15 px past
  the content edge, and 24 px past it (into the window edge) while recording.
- Change: the width is computed the way the row is laid out. Measured on a
  1360 px wide window: the text ended at x = 1354 before and ends at x = 1339
  now; the cards end at 1340.

### L1. Some valid field widths are rejected (libaoahid)

- Where: `libaoahid/src/hid/descriptor_builder.cpp#L190`.
- Why: HID 1.11 section 8.4 lets a field touch at most four bytes. The
  generator pads between field groups, but not between two caller-sized
  fields that follow each other directly. A 32-bit Y behind a 31-bit X, or an
  X of 29 bits or more behind a 4-bit Contact Identifier, was rejected
  although `docs/LIMITS.md` said every width combination is kept valid. The
  player's touchscreen setup accepts widths up to 2147483647, which libaoahid
  then refused above 268435456.
- Change:

  ```cpp
  // after, at the start of DescriptorBuilder::variable()
      const std::size_t lead_bits = input_bits_ & 7U;
      if (lead_bits != 0U && lead_bits + bit_width > 32U &&
          !constant_padding(static_cast<std::uint16_t>(8U - lead_bits))) {
          return false;
      }
  ```

- Effect: only inputs that were errors change. The golden descriptors are
  byte-identical. Test: `test_field_span_padding`.

### L2. A closed Device can stay open up to 60 s (libaoahid)

- Where: `libaoahid/src/api/c_api.cpp#L252`.
- Why: when `aoahid_device_close` cannot destroy a Device at once it hands it
  to the Context graveyard, which the event thread reaps after a poll. If the
  last callback finished after the close's final check but before the
  hand-over, the event thread had already looked and gone back to its
  60-second wait, and nothing woke it.
- Change: the event thread is interrupted right after the hand-over.

### L3. Context mutex locked on every submit (libaoahid)

- Where: `libaoahid/src/api/c_api.cpp#L210`.
- Why: in internal-thread mode `aoahid_node_submit` locked the Context mutex
  only to find that no error was latched.
- Change: an atomic flag mirrors the latch and is read first. The lock is
  taken only when an error is pending.
- Note: tests that write `deferred_error` directly must set the flag too.

### L4. Two statements in the docs contradict the code (libaoahid)

- `aoahid.h`, `aoahid_spec_create_toggle`: a Camera Control Usage other than
  Auto-focus or Shutter returns `AOAHID_ERR_PARAM`; the comment said
  `AOAHID_ERR_UNSUPPORTED`.
- `docs/LIMITS.md`: a Logical Maximum is written unsigned when both extents
  are non-negative (`libaoahid/src/hid/item_writer.cpp#L95`);
  the table said it is always written to read correctly as signed.

### X1. After the device is lost the port accepts connections that nothing answers (proxy)

- Where: `aoahid_adb_proxy/src/aoahid_adb_proxy.cpp#L228` (`accept_loop`).
- Why: a failed USB read ends the session, but the listening socket stayed
  open and unserved until `aoahid_adb_proxy_stop`. `adb connect` then
  connected and hung.
- Change: a `lost` flag, set by the thread that reads USB. Once it is set the
  accept thread closes every new connection as soon as it is accepted. The
  port stays bound until `stop`.

  ```cpp
  // after, in accept_loop()
      if (ctx->lost) {
          closesocket(client);
          continue;
      }
      serve(ctx, client);
  ```

- 3.1.1 closed the listening socket instead. That was withdrawn in 3.1.2: it
  freed the port while adb could still list `127.0.0.1:<port>` as the phone,
  so another local program could bind it and answer in the phone's place.
- Test: `test_channel_lost` checks that later clients are turned away, that
  nothing reaches the device, and that the port stays bound.

### X2. Source fallback pinned by tag name (proxy)

- Where: `aoahid_adb_proxy/CMakeLists.txt#L22`.
- Change: the `FetchContent` fallback names the commit of `v4.0.0`, so moving
  the tag cannot change what is built.

## Part 2: open

Each item names the place, the reason, and a change that would address it.
None of these was applied: each either needs a decision, needs hardware to
confirm, or is larger than a fix.

### O1. Transfer pool spinlock is held across `libusb_submit_transfer` (libaoahid)

- Where: `libaoahid/src/transport/transport.cpp#L286`.
- Why: the event thread's completion path spins on the same flag. If the
  submitting thread is preempted inside the system call, the event thread
  spins for the whole preemption.
- Proposal: mark the slot submitted under the lock, release it, submit, and
  re-take it only on failure. `cancel_all` must then handle a slot marked
  submitted that libusb does not know yet. Effort M.

### O2. `Channel::open` can return OK for a Channel that is already lost (libaoahid)

- Where: `libaoahid/src/transport/channel.cpp#L307`.
- Why: in stream mode, when a later read-ahead submit fails while an earlier
  one is in flight, open returns `AOAHID_OK` and the real status is lost; the
  first read reports `AOAHID_ERR_NO_DEVICE`.
- Proposal: keep the failing status and return it from the first read.

### O3. Zero-length packet rule uses the larger of the two packet sizes (libaoahid)

- Where: `libaoahid/src/transport/channel.cpp#L259`.
- Why: `max_packet` is the maximum of the IN and OUT `wMaxPacketSize`. An
  interface whose two endpoints differ would get the OUT rule wrong. ADB
  interfaces use one size for both, so no failure is known.
- Proposal: keep the OUT size separately and use it for the rule.

### O4. A halted bulk endpoint is never cleared (libaoahid)

- Why: the library does not call `libusb_clear_halt`. After a STALL on the
  OUT endpoint every later write fails, and after one on IN the Channel is
  lost. The caller has to close and reopen.
- Proposal: decide whether a Channel should clear a halt itself or report it
  distinctly so the caller can.

### O5. A signal can end an ADB session (proxy)

- Where: `aoahid_adb_proxy/src/aoahid_adb_proxy.cpp#L107`.
- Why: `send` returning -1 with `EINTR` is treated as a lost client. That
  happens only in a host that installs signal handlers without `SA_RESTART`.
- Proposal:

  ```cpp
  const auto n = send(...);
  if (n < 0 && errno == EINTR) continue;   // POSIX only
  if (n <= 0) return false;
  ```

### O6. The owner cannot ask whether the proxy still serves (proxy)

- Why: after a lost Channel the proxy is idle until `stop`. Since 3.1.2 a
  new connection is closed at once, which shows it from outside, but the owning program has no call to
  ask. The GUI keeps showing the bridge as on.
- Proposal: `int aoahid_adb_proxy_running(const aoahid_adb_proxy_context*)`,
  a minor release, and a check in the player where it reports bridge state.

### O7. A failed device is closed on the playback thread (player)

- Where: `aoahid_player/src/device_group.cpp#L107`.
- Why: closing stops the bridge (up to about 1 s) and drains the device (up
  to 1 s). With several phones, unplugging one holds up input to the others
  for that long.
- Proposal: mark the slot inactive in `fail` and close it in `reset`, or
  after the run. Effort M; needs a check of what libaoahid does with an
  unplugged device that is left open.

### O8. A repeat lap of zero length is not paced (player)

- Where: `aoahid_player/src/player.cpp#L396`.
- Why: a script whose repeated rows all have `wait_ms` 0, played with no loop
  limit, sends reports as fast as USB completes them and reports a lap each
  time.
- Proposal: refuse it when the script is loaded, or warn once and stop after
  the first lap.

### O9. The timeline sum can overflow (player)

- Where: `aoahid_player/src/event_script.cpp#L622`.
- Why: one row may wait up to 1e9 ms; about 9200 such rows overflow `int64_t`
  nanoseconds.
- Proposal: reject a script whose total exceeds a stated bound when loading.

### O10. `ABS_X` and `ABS_Y` are read as the selected slot's position (player)

- Where: `aoahid_player/src/getevent_parser.cpp#L261`.
- Why: a driver that also emits single-touch emulation sends `ABS_X`/`ABS_Y`
  for the oldest contact at the end of a frame, when another slot may be
  selected. Not confirmed against a device's output.
- Proposal: capture `getevent -lt` from a panel that emits both, then decide.

### O11. `run_command` may wait without a timeout (player)

- Where: `aoahid_player/src/process.cpp#L510`.
- Why: once the child has closed its output, the wait for it to exit has no
  limit. Not reproduced.
- Proposal: apply the remaining time to that wait and terminate on expiry.

### O12. Input routes answer `ok` when Live control is off (player GUI)

- Why: this is the documented behavior ("silently no-ops"), but a caller
  cannot tell that nothing was sent.
- Proposal: answer 409 with "Live control is off" from the input routes. It
  changes documented behavior, so it belongs in a minor release with a README
  change.

### O13. A full live inbox drops presses and releases (player GUI)

- Where: `aoahid_player/apps/aoahid_player_gui/engine.cpp#L17`.
- Why: past 4096 queued items everything is dropped, including a release,
  which leaves a control held on the phone until Live control stops.
- Proposal: when full, drop moves only.

### O14. A failed bind turns the saved Control API switch off (player GUI)

- Why: when the port is taken at startup, the switch is cleared and that
  state is saved, so the user's choice is lost.
- Proposal: keep the saved choice separate from whether the server runs.

### O15. Turning the Control API off can block the window for 5 s (player GUI)

- Where: `aoahid_player/apps/aoahid_player_gui/control_api.cpp#L335`.
- Why: stopping joins the server, which waits for a request that is waiting
  for the UI thread.
- Proposal: answer pending UI requests with 503 before joining, as the
  destructor already does.

### O16. Images are read whole with no size limit (player GUI)

- Why: a very large file named as the reference image or background is read
  into memory at startup; an allocation failure there ends the program on
  every start until the settings file is edited.
- Proposal: refuse files above a stated size before reading.

### O17. The adb server is stopped at startup and on refresh (player GUI)

- Why: it frees the phone's ADB interface, but it also ends adb sessions the
  user has with other devices and other tools.
- Proposal: stop the server only when a bridge needs the interface (the
  bridge start already retries after stopping it), or add a setting. This
  changes when a device can be opened on Windows, so it needs hardware.

### O18. `adb` is found through the default Windows search order (player)

- Where: `aoahid_player/src/process.cpp#L98`.
- Why: with no application name, `CreateProcessW` looks in the program's own
  folder and the current folder before `PATH`. Not tested on Windows.
- Proposal: resolve `adb` on `PATH` and pass the full path.

### O19. `Player`, `DeviceGroup`, `Session`, and `Engine` have no automated tests

- Why: they need a device. The fixes P1, P2, P3, P4, and G3 above were
  checked by hand or by reasoning only.
- Proposal: a test build of the core against definitions of the libaoahid
  functions it calls, the way the proxy's test replaces the four Channel
  functions. Effort L.

### O20. The player compares a libaoahid diagnostic string

- Where: `aoahid_player/src/context.cpp#L116`.
- Why: whether a timed-out context destroy kept ownership is decided by
  comparing `aoahid_last_error()->field` with a literal.
- Proposal: a distinct result code, or a documented guarantee for that field
  in `aoahid.h`, in a libaoahid minor release.

### Design notes for the GUI

Observed in screenshots of 1.0.2 at 1360 by 900 and 1000 by 640. None is a
defect.

- The Glass card's *Clear* slider (transparency) shares its name with the
  *Clear* buttons (which remove something). Another name for the slider would
  remove the ambiguity.
- Text contrast in the solid themes is above 4.5:1 for the dim and faint text
  tokens on the window and card backgrounds, so no change is proposed there.
- `App::current_settings()` builds and compares a full settings snapshot on
  every frame with no active widget. Comparing on change would remove those
  allocations.
